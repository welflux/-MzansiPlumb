# Phase 4 implementation and release limits

The workspace now supports owner, administrator, dispatcher, supervisor, technician, finance and read-only management roles. Effective roles live in `member_roles`; the legacy `users.role` remains a compatibility value, not an authorization source. Every authenticated request decorates the role and branch memberships from the database. Owners and administrators have company-wide operational scope. Billing, account deletion and legal holds are owner-only. Other roles have assigned-branch scope; technicians additionally need a job assignment. Membership, role and branch changes revoke affected sessions. Work records and private evidence are excluded from finance/management permissions. Branch creation/reactivation, active members and job creation have transactional plan limits. Job counts include cancelled jobs, using the SAST calendar month.

Organization, workload, internal approvals, service pricing, document branding, privacy and subscription pages are connected to persistent APIs. Main branch is initialized for existing/new workspaces. Teams, customers, stock, contracts, jobs, service areas and generated follow-ups carry branches. Inactive branches cannot accept assigned work. Existing job branches are immutable through the regular editor. Service areas use configurable four-digit postcodes; no geocoding or invented routing is claimed.

Approval policies support a ZAR quotation threshold, approver roles and an optional different-person requirement. Approval hashes include exact content and policy versions; changes require a fresh decision. A used approval cannot be reused. Approver access is checked again at consumption. Internal authorization never implies customer acceptance. Customer quotation links still record self-declared identity, not verified identity or a signature.

Company logos are normalized private PNGs. Branding is included in issued quotation and completion snapshots and rendered on quote/job-card/service PDFs. Draft/open documents use current branding. The supplied MzansiPlumb brand remains the application brand; no landing redesign was made. ZAR prices are integer cents; quote totals/VAT are recomputed server-side. VAT registration, number and rate are company-configured facts and are not validated against SARS. Phone numbers normalize South African `0xxxxxxxxx` to `+27xxxxxxxxx`, or accept international E.164 form; ownership/deliverability is not verified. Dates are shown in SAST/en-ZA.

## Privacy and deletion

Company administrators can reauthenticate and stream a full NDJSON export, including private file bytes encoded as base64. Credentials/session/approval hashes/provider tokens are excluded. Export is retained when evaluation/subscription write access ends. Store downloaded exports securely. Branch users have scoped operational CSV reports rather than full-company exports.

Contact privacy hides customer email/phone from technician API/PDF output. Retention days are a documented review preference, **not automatic erasure**. An owner may request deletion with password and exact company name. Seven days must elapse; writes pause, other sessions revoke and company email disables. The owner may cancel. Erasure additionally requires a retention review, backup/external-record acknowledgment, no active hold and cancellation of an existing real provider subscription. Database records are actually removed transactionally. A hold requires operator/legal review to release; there is no public bypass. Application erasure cannot claim to erase provider records or retained backups.

Before production, establish lawful retention, data-subject handling, vendor agreements, incident response, access-review procedures, encrypted backup expiry, export handling, and legal/tax review. Do not claim POPIA/tax compliance or plumbing certification. Restoring a backup can restore deleted data: maintain a separate restricted deletion register and reapply completed deletions before reopening access. The application does not silently certify or create compliance certificates.

## Subscription behavior

New/existing workspaces receive a clearly labelled 14-day development evaluation. It is not a paid subscription. Proposed Solo/Team/Business/Enterprise limits are seeded, with all prices NULL and unpublished. These are configurable catalog defaults, not approved commercial offers. `node scripts/configure-plan.mjs /private/approved-plan.json` validates and updates catalog prices/limits/features; it never activates billing or self-assigns a paid plan. See `server/entitlements.mjs` for feature keys. Required JSON fields: id, users_limit, jobs_limit, branches_limit, features (array), price_cents (ZAR integer/null), paypal_price_cents (USD integer/null), paypal_plan_id (string/null), published (boolean).

Expiry/suspension/payment failure after a bounded seven-day grace stops operational writes. Read access, reauthentication, billing recovery and owner privacy workflows remain. Cancellation retains access only to the stored period end. Maintenance generation and outbound reminders also check access; API routes cannot bypass quotas with teams or background jobs. Existing premium records remain readable after expiry; premium mutations require the feature. No tenant API grants itself a paid plan.

## Payments: implemented but NOT release verified

**Keep `BILLING_ENABLED=false` and `BILLING_ACTIVATION_APPROVED=false` until the user explicitly approves activation.** Default/sandbox mode does not imply permission to activate live billing. No merchant account was connected, no checkout was made against a provider and no money moved.

The abstraction includes PayFast hosted recurring card checkout in ZAR and PayPal Subscriptions in separately approved USD (no automatic ZAR conversion and no Stripe). These are candidate integrations pending merchant/provider review, not a claim of actual South African availability. On 2026-10-17 the environment proxy returned `403 CONNECT / Domain forbidden` for the official PayPal South Africa and PayFast documentation sites. Thus SA merchant onboarding, recurring-card availability, supported settlement/currencies, withdrawal/FNB requirements, fees, refund/dispute behavior, API details and plan eligibility remain **unverified**. A reviewable environment network draft adds the official documentation domains; it must be saved/published through environment settings to apply.

Authoritative references to review when access is available:
- https://www.paypal.com/za/business/accept-payments
- https://developer.paypal.com/docs/subscriptions/
- https://developer.paypal.com/docs/api/webhooks/v1/#verify-webhook-signature_post
- https://developers.payfast.co.za/docs
- https://www.payfast.co.za/

Both adapters require activation flags, a merchant-review evidence reference, a random 32-byte base64 `BILLING_TOKEN_KEY` and provider credentials. Store all server-side, never `VITE_*` or source control. PayFast: `PAYFAST_MERCHANT_ID`, `PAYFAST_MERCHANT_KEY`, `PAYFAST_PASSPHRASE`. PayPal: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID` plus a matching ACTIVE monthly regular no-trial/no-setup-fee USD plan ID/price in the catalog. `BILLING_ENV=sandbox` is the default; live requires explicit review and approval. The token encryption key is required for cancellation and recovery; back it up separately and define rotation before use.

Checkout only returns the real provider approval destination/signed hosted form. Returning to `/app#subscription` never upgrades access. PayFast callbacks verify signature/merchant, exact amount/currency and provider server validation. PayPal callbacks call its webhook verification API and authoritative subscription lookup, bind checkout/plan and require actual payment amount plus a future period for activation. Provider tokens are encrypted, events/receipts deduplicated transactionally. Invalid/unverified events never grant access. Disabled processing quarantines verified callbacks. Failed requests return errors for provider retry; provider events are the durable replay ledger. Public cookie/Origin exemptions are limited to authenticated provider webhooks.

Register reachable HTTPS endpoints `/api/webhooks/payfast` and `/api/webhooks/paypal`; provider posts do not have browser Origin/CSRF. Configure PayPal subscription lifecycle and payment-sale-completed events. Verify the exact subscribed events against current provider docs. Confirm egress to official APIs, sandbox/live destination separation, production CSP form-action, proxy body/header preservation and redacted logs. Never enable by guessing credentials or trusting browser success flags. Tests use explicitly labelled fixture transports, signatures and artificial test records; these are not provider round trips or commercial payment evidence.

Before activation, reconcile specs against accessible official docs, complete SA merchant onboarding, run sandbox approval/payment/failure/renewal/cancel/replay/mismatch tests on the actual account, verify signed callbacks over public HTTPS, reconcile receipts with provider ledgers, document operator retry/recovery/refund/dispute handling and receive user activation approval. Plan changes while a provider subscription exists require a reviewed cancellation/replacement; self-serve upgrades/proration are deliberately blocked. Automated dunning email, provider refunds and financial reconciliation dashboards are not implemented.

## Deployment and verification

Apply migrations 003–005 automatically through `openDatabase` on startup after a verified encrypted backup. Do not edit already-applied migrations in a deployed environment. Single-node Node 24, native sharp, writable private persistent SQLite WAL storage and a supervised automation process remain required. Hostinger compatibility is still unverified until the user supplies the plan. See HOSTINGER-DEPLOYMENT.md. No deployment was performed.

Run `npm run build`, `npm run test:api`, `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm test`, `npm audit --omit=dev`. Tests cover existing workflows plus roles/branches, quotas/background generation, approval versioning/two-person rules, branding PDFs, phone/contact controls, export/deletion, default-off billing, PayFast duplicate signatures and PayPal authoritative activation/failure/cancel states. No provider network calls occur in tests. Large-company load, multi-instance deployment, independent penetration review, disaster recovery with real providers and Hostinger runtime are not verified. The supplied original landing artwork/logo still are not available to the build as local assets; the asset release check remains blocked. This release must not be called production ready.
