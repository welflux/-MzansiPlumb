# Phase 3 — advanced operations

This phase extends the existing Node 24 / Express / SQLite workspace. The approved landing-page layout and stylesheet remain unchanged. Billing and live payments remain disabled; there is no payment provider or charging endpoint.

## Connected operational features

- Overview includes actionable overdue jobs, unassigned work, incomplete in-progress records and outstanding quotation decisions. Counts and expandable lists use actual authorized records. Technicians see their assigned work; dispatchers/owners see their company.
- The follow-up queue combines required manual next steps with automatic overdue, assignment, appointment, incomplete-record, quote-decision and recurring-service tasks. Tasks can be snoozed or marked handled with a recorded reason. Handling a task **does not** approve a quote, sign off work or complete a job. Automatic tasks resolve when their source condition clears; manually handled tasks remain in history.
- In-app reminders are durable records, generated once per due task per South African calendar day. Appointment reminders become eligible 24 hours ahead and remain actionable for unfinished visits. Quote follow-ups become due at the earlier of expiry or two days after issue; expired undecided quotes remain a follow-up to revise/contact the customer. Overdue and required-next-step reminders recur daily while open and due. Low-stock reminders include the recorded available balance and threshold. The shared company inbox can be marked read independently of completing its tasks.
- Recurring maintenance schedules belong to a customer/property, optionally apply a service template, and specify a day/month interval, next due time and lead window. Processing generates a real unassigned job and linked occurrence for each due service. Unique occurrence keys prevent duplicate jobs on retries/restarts. Calendar-month schedules retain their original day and clamp short months; ordinary edits do not accidentally reset a clamped anchor. Up to 12 missed occurrences per contract are caught up per pass. Archived sources produce a blocked-maintenance reminder; schedules can be paused without deleting generated jobs.
- Stock items have company-specific SKUs, units, reorder thresholds and configured unit costs. Opening balances, receipts and corrections require ledger movements and reasons. Stock-linked job-card material rows consume stock atomically with the card save. Re-saving unchanged usage does not consume again; reducing/removing usage returns the difference. Negative stock and stale edits are rejected. Existing job usage retains its first captured unit cost; changing a stock item's default affects new usage on other jobs. Units cannot be changed on an existing SKU. Free-form material records remain supported without pretending they affected inventory.
- Job costing uses recorded labour minutes, configured hourly cost, stock-usage cost snapshots, entered unit rates for free-form materials, allocated overhead and named other costs. Missing labour/material costs are flagged; partial known totals are not presented as final profit. Company defaults may be set by the owner, and saving a job cost record snapshots the chosen rates. Accounting annotations can be corrected after a job closes without changing its completion evidence.
- Revenue is an explicit manual accounting ledger against completed jobs, with recognition date, net amount, unique external-document reference and explanatory note. There is no inferred revenue from quote acceptance, no generated invoice, no collection claim and no payment processing. Corrections add a linked negative reversal instead of deleting history. Reports show revenue recognized in the selected SAST date range separately from accepted quote value, jobs completed, recorded labour and known job costs. Per-job contribution is available only when revenue and required cost inputs exist; it uses that completed job's all-time recorded revenue. CSV exports escape spreadsheet-formula prefixes.
- Service templates hold company-defined descriptions, categories and required/optional checklist items. New jobs copy the selected template; editing a template does not change existing job requirements. Technicians save actual checklist results or not-applicable reasons, and required checks are enforced at completion. No legal compliance or certification is hardcoded or implied.
- New completions atomically capture company/customer/property/work/technician details and evidence SHA-256 hashes. Reports use that snapshot; altered/missing photo bytes or changed snapshot content fail integrity checks. Authorized users can download the completion record. Older completed jobs are not retroactively claimed to have a contemporaneous snapshot. These database/hash checks are **not** an independently signed or notarized proof; a database administrator could replace both content and hashes. Customer signatures remain unimplemented and explicitly absent. Actual private-link quote decisions remain separate from work completion.
- Company audit history includes actor, source (user/customer/system), action and timestamp, with cursor pagination. It covers maintenance generation, task handling, stock usage/corrections, templates, costs, revenue/reversals and notification outcomes. No secret values are stored in audit records.

## Reliable scheduled processing

The API runs a durable automation pass at startup and every 30 seconds by default. Queue state, idempotency keys, attempts, leases and heartbeat are stored in SQLite; the timer itself is not the persistence mechanism. Restarting reconciles current records and resumes eligible work. A database lease prevents concurrent passes; outbox claims have their own lease tokens so stale workers cannot overwrite newer claims.

- `npm run dev:all`: frontend and API with the embedded worker.
- `npm start`: built frontend/API with the embedded worker in production mode, after deployment prerequisites are verified.
- Set `AUTOMATION_ENABLED=false` to disable only the API's embedded worker. Run `npm run worker` under a process supervisor for a separate continuously running worker, or schedule `npm run worker:once` every minute using the provider's scheduler. Explicit worker commands still process work when the API's embedded timer is disabled.
- Both worker modes use the same DATABASE_PATH, private local volume and environment configuration as the API. Do not point them at unrelated/test databases or a network-shared SQLite volume. Multiple API instances remain unsupported; lease handling permits overlap between scheduler/worker invocations.
- Automation & inbox reports the last successful pass, failures and a stale heartbeat after two minutes. A stopped host/process cannot run reminders: configure a supervisor/scheduler and external health monitoring on the actual host. The “Refresh automatic queues” action reconciles the signed-in company's in-app queue only; it does not itself call an email provider.
- Transient tick failures persist an error and are retried by the next pass. Email 429/5xx/network failures retry with exponential backoff starting at one minute, up to five attempts. Permanent provider rejections fail explicitly. Processing claims abandoned by a crashed process become eligible after their lease expires.
- Every external retry uses the same Resend idempotency key. Automatic retries stop 23 hours after record creation to stay conservatively inside the provider's idempotency window; never-attempted reminders older than 48 hours are suppressed. Terminal failures require operator review; there is no blind manual resend of uncertain/accepted mail. Unresolved tasks generate a new daily reminder through the ordinary queue.
- Disabling email, changing its recipient, resolving/snoozing a task or restocking an item suppresses eligible unsent reminders. It cannot recall a request already accepted by a provider. Delivery attempts and their outcomes can be inspected from the inbox.

## Real optional email delivery

In-app reminders work without external credentials. **No live email was sent or verified in this implementation.** Email is off by default and cannot be enabled without the required server configuration. SMS and automatic customer messaging are not implemented. The supported email destination is an internal company operations/dispatch address chosen by the owner; the app never emails customers merely because they have a pending quotation.

To configure Resend after authorization:

1. Verify a sender domain in Resend and provide RESEND_API_KEY, NOTIFICATION_FROM (plain email address) and RESEND_WEBHOOK_SECRET securely in the server/worker environment. Do not put these values in client VITE_* settings, source control or chat. Existing environment metadata and variable names were checked; these bindings are absent in the current instance.
2. Allow outbound HTTPS to `api.resend.com` using the environment/hosting network controls while preserving existing destinations. Startup scripts use Node 24's `--use-env-proxy` so configured HTTP(S) proxies and normal CA trust remain in effect; TLS verification is not disabled.
3. Register the public HTTPS endpoint `/api/webhooks/resend` for email.delivered, email.bounced and email.complained (email.sent is also safely accepted). Configure its webhook signing secret on the API. The handler validates Svix HMAC signatures and a five-minute timestamp window, deduplicates event IDs and handles events arriving before the send acknowledgement.
4. In Company workspace → Automation & inbox → Email settings, choose the real internal recipient and enable reminders. “Credentials present” is configuration evidence only; it does not prove provider authorization, sender verification or callback reachability. No messages are sent merely by saving credentials while the company toggle is off.
5. Run a controlled staging test to an authorized address. Verify the outbox goes from pending/processing to **accepted** only after a provider response supplies a real message ID, and to **delivered** only after a valid signed delivered event. Accepted is explicitly labelled delivery-unconfirmed; delivered means the provider reported mailbox acceptance, not that the person read it. Bounces/complaints fail explicitly. Verify bad signatures are rejected, worker restarts do not duplicate the message and disabling prevents new sends.

The local automated tests replace the external transport with a controlled test response and construct signed callback fixtures. They validate application behavior, not a live Resend account. Browser-test processes explicitly clear provider credentials and cannot send email. Live credential/domain/webhook/egress validation remains outstanding.

## Validation and limitations

Run `npm run build`, `npm run test:api` and `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm test` in this machine. The API suite uses temporary databases; browser tests use `var/browser-tests.sqlite`. The ordinary `var/mzansiplumb.sqlite` has no seeded users. API PDF tests require `pdftotext`. Browser tests cover desktop, mobile and small-mobile workflows; accessibility checks include registration, customer records, automation and reports.

The suites exercise persistent workflows, tenant/role isolation, stock deltas/shortages, cost maths and unknowns, actual revenue/reversals, calendar-month anchors, maintenance deduplication, checklist completion, evidence integrity, durable queues/restarts, worker claims, transient/permanent failures, retry limits, disabling, idempotency headers, early/duplicate/signed callbacks, stale reminder suppression and rate-limit isolation. They do not substitute mocked records for application workflows; only the external delivery provider is controlled in tests.

Production blockers from Phase 2 remain: target Hostinger Node 24/native-library/persistent-disk compatibility, recovery/email verification/MFA policy, PDF malware scanning, POPIA operating controls, provider recovery drills and formal security/load testing. The original landing artwork is still inaccessible to the build; its visual release check still fails. Large-company load and multi-instance deployment are unverified. Some lists are bounded (follow-ups 500, inbox 200, per-item movements 200, occurrences last 24); audit has cursor pagination. Retention/archiving of long-lived queues and provider event/attempt history must be agreed before production.

Backup/restore now includes all Phase 3 tables.
