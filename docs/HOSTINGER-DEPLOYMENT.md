# Hostinger deployment gate and procedure

**Deployment is deferred until the user provides the intended plan and domain. This procedure has not been verified on a Hostinger account. Do not claim deployment or production readiness.**

Required hosting capabilities: Node 24.x (built-in node:sqlite), a persistent writable private local volume, a supported Linux native Sharp build, a managed long-lived Node process, sufficient memory for image/PDF work and concurrent 128 MiB scrypt hashing, HTTPS routing to that process, and a scheduler/operator mechanism for encrypted backups. Static hosting alone is insufficient; PHP-only shared hosting cannot run this backend. Do not purchase or upgrade a plan without explicit authorization.

After plan capabilities and security requirements are confirmed:

1. Prepare a separate staging website/process and database. Upload/clone the exact application release without .env, var/, test results, backups or node_modules from another operating system. Preserve the existing checkout when developing; do not create a worktree unless requested.
2. In the build environment use Node 24.x, then `npm ci`, `npm run build`, `npm run test:api` (requires Poppler's pdftotext), and the browser suite with Chromium installed. Preserve the lockfile. Review `npm audit`. Resolve the original-artwork check before visual release. Build dependencies must be available at build time; the runtime only needs production dependencies and dist/ plus server/ and scripts/.
3. Set NODE_ENV=production, exact APP_ORIGIN=https://the-confirmed-domain, the provider-assigned PORT, appropriate HOST binding for its reverse proxy, and DATABASE_PATH to the verified persistent private path. Default HOST is loopback; a provider requiring 0.0.0.0 must explicitly supply that value. Never put the database under public_html or dist. Configure secure environment values in hPanel/service settings; no application secret belongs in client VITE_* variables.
4. Start `npm start` from the project directory. It serves both the built frontend and /api using one same-origin process. Migrations apply at startup inside transactions. Back up before every release that introduces migrations. Ensure only one application process uses this SQLite database. Use the provider's process manager and restart-on-failure mechanism rather than an SSH shell session.
5. Confirm /api/health returns `status: ok` and `billing_enabled: false`. Confirm /app and private approval routes serve the frontend; API paths must reach the Node process, not static fallback HTML. Configure TLS, proxy upload limits of at least 8 MB plus multipart overhead, sensible timeouts, no caching of /api or private approval pages, and suppression/redaction of approval tokens in access logs. Security headers are supplied by Helmet; verify the proxy preserves them.
6. Test an actual staging workspace with the full customer-to-report workflow, separate tenants, technician access, session revocation, secure cookies and quote decisions. Validate exact-origin rejection, upload/download privacy, SAST input/output, VAT settings and native image handling. Confirm data survives a managed process restart and a deployment; a port opening is not persistence proof.
7. Configure encrypted off-machine backups and a scheduler with the securely stored BACKUP_ENCRYPTION_KEY, then perform a recovery drill. See BACKUP-RECOVERY.md. Do not assume provider backups include the private volume or that a deployment backup contains recent WAL changes.
8. Resolve the security and account-recovery blockers in SECURITY.md before public traffic. Create the real company using normal registration only after those gates. There are no default credentials or seeded demo accounts. Billing/live payments remain disabled.
9. Promote staging only after user review of the concrete target deployment. For rollback stop traffic, restore the compatible release and verified database snapshot to a new path, switch DATABASE_PATH, restart and repeat readiness/privacy checks. Down-migrations are not supplied; do not run older code blindly against an upgraded database.

Provider-specific hPanel field names, account resources, domain/DNS changes, scheduler commands and service restart mechanics must be filled in from the selected plan's actual capabilities. No Hostinger resources were created or modified in this phase.

## Phase 3 worker and email additions

The API now starts the durable automation loop by default. Verify maintenance generation, shared database leases, outbox recovery and the persisted worker heartbeat across managed restarts. If the plan needs a separate worker/scheduled command, set AUTOMATION_ENABLED=false for the API and supervise `npm run worker`, or schedule `npm run worker:once` every minute with the same private DATABASE_PATH and secure environment. Startup commands use Node 24's --use-env-proxy; preserve configured proxy and CA settings. Do not rely on a browser tab or ephemeral SSH process for scheduling.

Email is optional and off by default. Resend requires securely configured RESEND_API_KEY, NOTIFICATION_FROM, RESEND_WEBHOOK_SECRET, outbound api.resend.com access, a verified sender and a public HTTPS signed callback at /api/webhooks/resend. A real staged delivery round trip must be verified before claiming email works. No credentials or live delivery were configured in Phase 3. Internal reminder emails do not approve customer work or collect payments. See PHASE-3.md for explicit queue states and retry semantics. Restored backups disable email and suppress uncertain unsent queue items until operator review.

Phase 4: keep both billing activation flags false, configure no payment credentials until merchant/provider review and explicit activation approval. The target must preserve public HTTPS provider webhook bodies/headers, allow provider API egress and run Node 24 with private persistent SQLite WAL files. Apply migrations 003–005 after backup and smoke-test all seven roles across branches. For payment prerequisites, provider docs blocked during implementation, exact credentials and release gates, see PHASE-4.md. These integrations have not been verified against a Hostinger plan or an actual merchant account.

## Phase 5 launch sequence (target confirmation still pending)

No Hostinger plan, account resource or domain has been confirmed in the session. No hosting/DNS change or purchase was performed. Do not assume that a plan marketed as Node hosting supports Node 24 built-in SQLite, retained local storage or this native dependency set. If the selected plan lacks any of these, choose an authorized compatible VPS or revisit the architecture before deployment; a static/PHP upload will not run the backend.

1. Confirm the actual plan, Node 24 binary/version, Linux architecture/Sharp support, private persistent volume path, process manager, port binding, reverse-proxy IPs, public HTTPS domain and scheduled backup support. Record these facts in the release checklist. For a VPS, `deploy/mzansiplumb.service.example` and `deploy/nginx.conf.example` are reviewable templates, not installed or verified server configurations. Resolve the service account, Node executable, release/data directories, domain/certificate paths and system hardening on the actual machine before using them.
2. Build/test the exact release: `npm ci`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:api`, `npm test` with Chromium available, `npm audit`, `npm run check:assets`. Resolve failed release checks. Upload only dist/, server/, scripts/, package.json and package-lock.json plus reviewed configuration. Install runtime dependencies with `npm ci --omit=dev` on the target; do not ship test databases, fixture secrets, browser artifacts, .env or node_modules from another system. Retain the source release separately for rebuilds.
3. Provision a private directory, for example `/var/lib/mzansiplumb` on a verified VPS, owned by the application service account with mode 0700. Use an absolute `DATABASE_PATH` outside the release/public web roots. SQLite WAL/SHM must stay with the database. This application does not use MySQL and cannot be pointed at a Hostinger MySQL URL. Back up any existing database before migration. Run `npm run migrate` with the exact production environment. Startup also applies missing migrations; no destructive down-migrations exist.
4. Set NODE_ENV=production, APP_ORIGIN to the exact HTTPS origin without a trailing slash, HOST/PORT for the confirmed proxy topology, DATABASE_PATH, AUTOMATION_ENABLED=true and independent random base64 32-byte BACKUP_ENCRYPTION_KEY and AUTH_LINK_KEY. Configure RESEND_API_KEY, verified NOTIFICATION_FROM and RESEND_WEBHOOK_SECRET securely; set AUTH_EMAIL_ENABLED=true only after sender/egress review. Set REQUIRE_VERIFIED_EMAIL=true for public production. `.env`, if used, must be service-account-only mode 0600. Prefer managed secret/service environment settings. Do not put values into frontend variables or Git. See .env.example for all optional settings.
5. Keep BILLING_ENABLED=false and BILLING_ACTIVATION_APPROVED=false. Finish merchant/specification/sandbox verification separately using PHASE-4.md; billing activation is a later explicitly approved action. Do not publish unapproved prices. Configure CLAMSCAN_PATH only if a real maintained ClamAV binary and current signatures are present and a target scan/rejection round trip has passed. Otherwise PDF attachments are deliberately rejected; normalized supported photos still work.
6. With a loopback-only Node backend and a verified local reverse proxy, use TRUST_PROXY_CIDRS=loopback. For another topology, supply only its actual CIDRs. Never set unconditional trust proxy or accept client-forwarded IP headers blindly. Restrict direct access to the backend port. Configure TLS/HTTP redirect, 9 MiB proxy body allowance, no caching of private endpoints, preserved webhook bodies/signatures and sanitized logs. The example Nginx proxy overwrites forwarded addresses and limits auth requests; syntax/certificate validation must be run on the selected server. Do not copy its DOMAIN/CERT placeholders verbatim.
7. Start `npm start` through the actual hosting process manager (or the reviewed VPS service). Verify GET `/api/health` for liveness and `/api/ready` for database/worker readiness (503 before the first healthy tick or after a stale heartbeat is expected). Run `npm run preflight` using the production environment. It checks local configuration/files/migrations and fails on unresolved prerequisites; success cannot prove external delivery, persistence, compliance or provider behavior. Configure external alerts for readiness, worker errors and disk/backup failures without logging private URL tokens.
8. Perform an actual HTTPS staging drill: register, request/receive/consume a verification email, verify unverified writes are blocked, log out, request/receive/consume recovery, verify expiry/replay/session revocation, then test separate companies/all roles/files/customer-to-report/export flows. Check signed mail callbacks separately from HTTP acceptance. Send real mail only under the authorized staging procedure. Check browser console/CSP and mobile/slow/error paths. Process-manager restart AND a deployment must retain real staged records and private files.
9. Run encrypted backup to private storage and restore to a new path. Verify data/files, session/challenge revocation, disabled reminders and suspended provider-backed subscriptions. Reconcile external payment state, pending checkout records and the deletion register before opening restored access. Schedule off-machine encrypted backups and test failure alerts/retention. The backup key must be stored separately and recoverably. A database file copied without a consistent SQLite backup/WAL process is not sufficient.
10. Close the remaining audit gates in PHASE-5-AUDIT.md, review the concrete staging result, then authorize promotion on the confirmed target. Roll back by stopping traffic/process, selecting a compatible prior release and restoring a verified database snapshot to a new private path; never run old code against an incompatible schema. Re-run health, privacy and persistence checks before traffic resumes.
